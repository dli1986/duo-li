## 1. 核心思想：父节点存的是文件偏移量，不是指针

普通的内存里的 B+Tree，父节点里存的是子节点的内存指针（`Node* child`）；这种架构反过来：**父节点里存的是子节点在文件里的偏移量（`offset_t child_offset`），而不是内存指针**。整个索引文件通过 `mmap` 一次性映射进虚拟地址空间之后，任何一个文件偏移量都可以直接转换成虚拟地址，不需要读文件、不需要反序列化、不需要单独维护一份内存中的树结构：

```text
virtual_address = mmap_base + file_offset
```

```cpp
void* mmap_base = mmap(NULL, file_size,
    PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);

// 用文件偏移量直接换算出虚拟地址，是整个架构最核心的一行代码
Node* get_node(offset_t file_offset) {
    return (Node*)(mmap_base + file_offset);
}

// 父节点存的 child_offset 本身就是一个文件偏移量，可以直接喂给 get_node
Node* get_child(Node* parent, int idx) {
    offset_t child_offset = parent->child_offsets[idx];
    return get_node(child_offset);
}

char* get_data(offset_t data_offset) {
    return (char*)(mmap_base + data_offset);
}
```

这样设计的好处是**文件里的字节布局就是内存里的字节布局**——磁盘上第 `0x1000` 字节处的节点，一旦被 `mmap`，在虚拟内存里就是 `mmap_base + 0x1000` 这个地址，两者说的是同一份数据，不需要"加载时转换成另一种内存表示"这一步。这也是为什么这类结构常被称为 zero-copy：文件内容本身就是可以直接使用的内存结构。

## 4. Byte Map：空闲页分配位图，不是"某页有没有 key"的存在性索引

这里的位图更准确的名字应该是 **Byte Map**——它对应的是常见存储引擎里"溢出块/空闲块分配器"的位图：核心操作是"O(1) 找一个空闲块分配出去、用完了再归还"，**从来不回答"这一页里有没有某个 key"**：

```cpp
uint64_t* byte_map = (uint64_t*)(mmap_base + 0x20000);

// 分配：找到第一个空闲页（bit == 0），标记成已分配（bit = 1）
int alloc_page() {
    for (int page_id = 0; page_id < total_pages; page_id++) {
        if (!(byte_map[page_id / 64] & (1ULL << (page_id % 64)))) {
            byte_map[page_id / 64] |= (1ULL << (page_id % 64));
            return page_id;
        }
    }
    return -1; // 没有空闲页了
}

// 释放：把对应 bit 清零，归还给分配器
void free_page(int page_id) {
    byte_map[page_id / 64] &= ~(1ULL << (page_id % 64));
}
```

- **每个 bit 对应文件里的一个页（block）**：`bit == 1` 表示这个页已经被分配出去在用，`bit == 0` 表示这个页是空闲的，可以被下一次 `alloc_page()` 拿走。
- **用途是给"分配器"用的，不是给"查找"用的**：正常按 key 查找 B+Tree，走的还是 root → internal → leaf 这条标准路径；Byte Map 只在"需要一块新页（比如叶子分裂、插入新叶子）"或者"一块页被删除、需要归还"的时候才会被访问，和查找路径完全无关。
- **随主文件一起 `mmap`、一起持久化**：Byte Map 本身就是索引文件的一段字节，进程重启后不需要重新扫描整棵树来重建分配状态。

### 可选：Bloom Filter（仅内存，这个架构目前没有这个结构）

如果确实需要"这个 key 一定不存在，可以跳过整页"这种能力，需要的是一个**概率型的 Bloom Filter**，这是和 Byte Map 完全独立的另一个结构：

- Bloom Filter 允许假阳性（说"可能存在"其实不存在），换来极小的内存占用，适合放在内存里做快速预筛；
- 它和 Byte Map 的关键区别：Byte Map 记录的是"页的分配状态"（精确、随文件持久化），Bloom Filter 记录的是"key 的存在性猜测"（概率型、通常只在内存里，不需要持久化）；
- **这个架构目前的设计里没有 Bloom Filter**——上面这一段是作为"如果要做这类查找优化，应该长什么样"的补充说明，标注为 Optional，避免把它误当成已经存在的机制。

## 5. Byte Map 本身也活在同一个 mmap 区域里

这个架构的另一个关键点是：**Byte Map 不是一个独立于文件之外的、只在内存里维护的结构，它就是同一个索引文件里的一段字节，同样通过 `mmap_base + offset` 访问**：

```text
virtual_addr = mmap_base + 0x20000 = Byte Map 在这次进程里的实际地址
```

这意味着 Byte Map 的更新（比如某个页被分配或者释放）会通过 `mmap` 的写回机制自动持久化到磁盘上，不需要额外写一份"位图快照"文件，也不需要在进程重启后重新扫描整棵树来重建分配状态——Byte Map 和树节点、叶子数据享有完全相同的持久化路径。

## 6. 文件布局：三段互不重叠的区域

整个索引文件在磁盘上按偏移量分成三段互不重叠的区域——这一点必须精确，如果某一段的边界估算错误，两段数据会在同一个偏移量上"打架"：

| 文件偏移范围 | 内容 |
| --- | --- |
| `0x0000` – `0x0FFF` | 文件头（magic、version、root 偏移量、节点数、data 起始偏移量等元信息） |
| `0x1000` – `0xFFFF` | 所有 B+Tree 节点（root、internal、leaf，每个节点固定占用一个 4KB 页） |
| `0x10000` 起 | 叶子数据记录（真正的 value，比如 `"John Doe, Age 25"` 这样的字符串） |
| `0x20000` 起 | Byte Map（空闲页分配位图） |

```cpp
struct FileLayout {
    FileHeader header;       // @0x0000
    BTreeNode  nodes[];      // @0x1000+
    DataRecord leaf_data[];  // @0x10000+
    ByteMap    byte_map;     // @0x20000+ 空闲页分配位图
};
```

**这三段之间没有重叠，是这个设计能够正确工作的前提**——任何一个偏移量在任意时刻只能属于其中一段。

## 7. 虚拟内存地址与文件偏移量的对应关系

下面是几个关键节点在"文件偏移量"和"这次进程里实际虚拟地址"两个维度下的对照，`mmap_base` 假设是 `0x7f8000000000`：

| 内容 | 文件偏移量 | 这次运行时的虚拟地址（`mmap_base + offset`） |
| --- | --- | --- |
| Root 节点 | `0x1000` | `0x7f8000001000` |
| Internal 节点 `[5]` | `0x2000` | `0x7f8000002000` |
| Leaf 节点 `[1,3,4]` | `0x5000` | `0x7f8000005000` |
| Key=1 的数据记录 | `0x10000` | `0x7f8000010000` |
| Byte Map（空闲页位图） | `0x20000` | `0x7f8000020000` |

右边这一列**每次进程重新 `mmap` 同一个文件时都可能不同**（`mmap_base` 由操作系统决定，不保证固定），但左边的文件偏移量永远不变——这正是为什么父节点必须存偏移量而不是指针：**指针只在当前进程、当前这次 `mmap` 有效，偏移量在文件的生命周期里永远有效**。

## 8. 查找的过程：标准 B+Tree 下降，只是每一步都换算成 mmap 地址

查找某个 key 的过程和普通 B+Tree 完全一样——从 root 开始，在当前节点的 key 数组里做二分查找，找到 key 所在的区间，取出对应的 `child_offset`，用 `get_node(child_offset)` 换算成当前进程里的虚拟地址，重复这个过程直到走到叶子节点，再在叶子节点内部查找目标 key。这个架构相对于"内存指针版" B+Tree 唯一的区别是：每次"走到子节点"这一步，做的不是普通的指针解引用，而是"偏移量 + `mmap_base` 的加法"——两者在 CPU 层面几乎一样便宜，但换来的是**整棵树可以直接以文件的形式持久化，进程重启后不需要重新构建，`mmap` 一下就能立刻在原来的偏移量上继续工作**。

## 9. 架构收益小结

- **Zero-Copy Loading**：`mmap()` 直接把文件映射进内存，没有"读取字节流 → 反序列化成对象"这一步，加载一个几十 MB 甚至几 GB 的索引文件的成本接近于零。
- **偏移量可移植**：文件偏移量在任何一次 `mmap`、任何一台机器上都表示同一份逻辑数据，不像内存指针那样只在当前进程这一次运行里有意义。
- **导航效率**：从父节点走到子节点，退化成一次加法 + 一次解引用，没有额外的查找表或者反序列化开销。
- **数据与索引物理分离，但共享同一套持久化机制**：树节点、叶子数据、Byte Map 在文件里各自占据独立区域，逻辑上分离、避免互相干扰；但因为都在同一个 `mmap` 区域里，天然共享同一套持久化（写回磁盘）和缓存（OS page cache）机制，不需要为 Byte Map 单独设计一套持久化逻辑。
